TRITON — Tiered Resource & Infrastructure Triage for Off-grid Networks

An AI-assisted energy management system for an isolated island microgrid — solar, wind, battery, and diesel backup — serving a hospital, a desalination plant, a school, and surrounding villages. Built for the DreamHacks hackathon; the deployment (Kailoa Island) is fictional, a simulation demonstrating a decision-making architecture, not production utility software.

The problem

Off-grid microgrids fail two ways today: a rule table ("if battery < 20%, shed load") that can't tell a failed sensor from a real event, or a dashboard with no control logic behind it. Both leave an operator alone to guess, exactly when a storm cuts both the power and their ability to call for help.

What TRITON is

Three layers, with a hard boundary between them:

Sensing (island_grid/sensors.py) — simulated telemetry at 15-minute resolution, including realistic faults (stuck sensors, equipment failures, fuel that runs out).
Deterministic dispatch (island_grid/optimizer.py) — the only layer allowed to decide anything: merit-order dispatch, priority-tiered load shedding (Tier-0 critical infrastructure is never auto-shed), fuel-limited diesel with scheduled resupply. Every cycle produces a structured decision trace and is checked against physical invariants by island_grid/validation.py.
Claude reasoning layer (island_grid/claude_advisor.py) — sits above the loop, never touches a breaker: a plain-language briefing, anomaly triage over correlated signals (not one threshold), and grounded Q&A over the actual decision trace.
Live Claude vs. offline fallback

With ANTHROPIC_API_KEY set, the reasoning layer calls the real Claude API. Without one, a deterministic fallback answers the same categories of question by reasoning over the same trace — every answer is labeled [Claude, live] or [Local fallback] so it's never ambiguous which ran.

This matters because the dashboard can only ever run the fallback — a published Artifact's browser sandbox blocks outbound API calls, full stop. That's a structural fact, not a shortcut, and the dashboard says so in its Architecture panel. The live path is real and runnable from island_grid/repl.py or the Python backend directly.

Running it
bash
pip install -r requirements.txt
python -m island_grid.simulate        # 72h simulation -> output/

export ANTHROPIC_API_KEY=sk-...       # optional
python -m island_grid.repl            # interactive console, live-Claude demo path

pip install -r requirements-dev.txt
python -m pytest                      # 37 tests

Dashboard: open frontend/index.html directly, or artifact/triton.html for the single-file version published as a Claude Artifact. No build step.

Sample result (72h run, fallback mode)
KPI	Value
Demand served	49,464 kWh
Energy shed	1.9% of demand (during the injected genset fault)
Diesel used	8,991 L vs. 13,850 L naive baseline — 35% less fuel
Anomalies flagged	35
Dispatch invariant violations	0 across 288 ticks

Honest finding from this run: battery storage, not diesel or solar capacity, is the binding constraint on renewable fraction — exactly the kind of question grounded Q&A is built to answer.

What's simulated vs. real
Component	Status
Sensor readings	Simulated
Dispatch decisions	Real, tested code
Decision trace	Real — generated live, not written after the fact
Dashboard Q&A	Deterministic fallback (sandbox constraint, see above)
Live Claude reasoning	Real, in the Python backend / REPL
72h KPI run	Real, checked into output/, test-validated
Repo layout
island_grid/          # sensors, optimizer, validation, Claude advisor, simulate, repl
tests/                 # pytest suite (37 tests)
artifact/triton.html  # published dashboard, single file (Claude Artifact)
frontend/             # same dashboard as real source — index.html, styles.css, js/
output/                # generated by simulate.py
